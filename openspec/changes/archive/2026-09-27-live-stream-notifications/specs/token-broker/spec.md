## Purpose

Covers the stateless backend service that performs provider token exchanges on behalf of the extension, so that platform client secrets never ship inside the extension bundle while official provider APIs remain the sole integration path.

## ADDED Requirements

### Requirement: Hold client secrets outside the extension

The system SHALL provide a backend service that holds the Twitch and Kick client secrets, and the extension bundle SHALL NOT contain any client secret. The service SHALL read its secrets from its own server-side configuration and SHALL NOT expose them in any response.

#### Scenario: Extension bundle contains no client secret

- **WHEN** the extension is built and packaged
- **THEN** its bundle contains no client secret for any platform
- **AND** all client-secret-bearing exchanges are performed by the broker service

#### Scenario: Secrets are never returned to callers

- **WHEN** the broker service responds to any request
- **THEN** no response body or header contains a client secret

### Requirement: Exchange an authorization code for credentials

The service SHALL expose an operation that accepts an authorization code, the parameters required to redeem it, and the proof-of-possession value generated by the extension, and SHALL perform the exchange against the platform's official token endpoint. The service SHALL forward only the parameters the platform requires and SHALL NOT persist the code or the resulting credentials.

#### Scenario: Successful code exchange

- **WHEN** the extension submits a valid authorization code and proof-of-possession value for a platform
- **THEN** the service exchanges it at that platform's official token endpoint
- **AND** returns the resulting credentials to the requesting extension

#### Scenario: Credentials are not retained

- **WHEN** the service completes a code exchange
- **THEN** it stores no copy of the authorization code, the access token, or the renewal credential

### Requirement: Issue application-level credentials for anonymous API access

Where a platform offers a client-credentials grant for public data, the service SHALL expose an operation that obtains and returns such a credential. The service SHALL keep the credential in its own transient memory, SHALL return it to the requesting extension, and SHALL NOT record it to any persistent store or log.

#### Scenario: Application credential is issued for public live-status data

- **WHEN** the extension requests an application-level credential for live-status queries
- **THEN** the service obtains it via that platform's client-credentials grant
- **AND** returns it to the extension
- **AND** writes nothing to persistent storage

### Requirement: Accept only the registered extension identity

The service SHALL accept exchange requests only from the extension's registered identity, and SHALL reject requests that do not present it. The service SHALL be served over HTTPS on a single known public origin and SHALL NOT accept credentials or codes on any other origin.

#### Scenario: Unregistered caller is rejected

- **WHEN** a request to the exchange operation does not present the registered extension identity
- **THEN** the service rejects it
- **AND** no exchange against any platform is attempted

#### Scenario: Service is reachable only over HTTPS on one origin

- **WHEN** the service is deployed
- **THEN** it is reachable over HTTPS on a single configured origin
- **AND** the extension contacts no other origin to perform an exchange

### Requirement: Never log secrets or credentials

The service SHALL NOT write authorization codes, access tokens, renewal credentials, or client secrets to logs, error reports, analytics, or error messages. When an exchange fails, the service SHALL report a reason that identifies the platform and the failure class without including the submitted values.

#### Scenario: Exchange failure is reported safely

- **WHEN** a platform rejects an exchange
- **THEN** the response identifies the platform and the failure class
- **AND** contains no authorization code, token, or client secret

#### Scenario: Service logs contain no credentials

- **WHEN** the service writes any log entry
- **THEN** the entry contains no authorization code, access token, renewal credential, or client secret

### Requirement: Survive restarts without user impact

The service SHALL be stateless, so that a restart, redeploy, or scale event does not invalidate any connected account. After a restart the service SHALL continue to perform exchanges and SHALL NOT require the user to reconnect accounts.

#### Scenario: Service restarts

- **WHEN** the broker service restarts
- **THEN** all previously connected accounts remain connected
- **AND** subsequent exchanges succeed without the user re-authorizing

#### Scenario: Service is redeployed

- **WHEN** a new version of the service is deployed
- **THEN** the service holds no state that must be migrated
- **AND** the user experiences no reconnection
